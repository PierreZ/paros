# The list of open causes (rule 8, docs/architecture/06-verification.md,
# step 1.4 of the rework, #1093 (heal scorecard and open causes)).
#
# One line per open liveness cause: `<phase>\t<message>`. The message is an
# `assert_always!` of the simulation, exactly as declared; the phase is the
# rework phase whose gate closes the cause. A red of an open cause is counted
# on the heal scorecard and does not fail a run. A safety cause is never on
# this list, and a cause that is not on it blocks.
#
# The list only gets shorter: a pull request may delete a line or move a cause
# to an earlier phase, never add a line or move one later (CI's
# `open-causes` job). Phase 7 ends when the list is empty and deleted.
#
# The first list is the liveness causes of five hunts of main at step 1.4
# (5,600 seeds; each cause red on 1 to 547 of 2,000 seeds) and of the CI
# sweep of its pull request (one cause, on one seed), with their phases.
# The phase of each cause is a reading of the gates of
# docs/architecture/07-changes-milestones-done.md §7.1, not a recorded
# decision: an operator operation that a chaos run leaves unfinished waits for
# the coordinator of phase 3 (rule 3, the cause "no coordinator"); a lost
# quorum, or a set or a control journal that is not its booked machines, waits
# for the recovery of phase 4 (rule 4, "a set does not reach its target inside
# the bound"); a gone member that a live machine can replace waits for the
# heal of phase 5 (rule 5, "a set has a member that is gone, and a live
# machine can take its place", "a dead id stays in the registry"); an admin
# view the cell does not answer waits for phase 3 ("an admin request is
# answered in the term that received it", "no coordinator"). An initial member
# that does not answer under its name waits for phase 5 ("an address written
# through the coordinator"). An election that does not settle on one leader
# waits for the pre-vote of phase 6 ("one leader holds in the end"). A node
# that does not catch up with the chosen prefix matches no gate before phase
# 7, so it waits for step 7.6; the gate of phase 1 examines it before phase 2
# starts.

3	fleet: a formed cell's control journals are learned through Inspect after chaos
3	fleet: a sent init forms a cell after chaos
3	fleet: a started init leaves the cell READY and joined after chaos
3	fleet: no tenant is left mid-operation after chaos
3	fleet: the directory and the cell's journal are read to their tails after chaos
3	heal: the cell answers an admin view within the bound
3	heal: the cell has a coordinator on a live machine within the bound
3	leads: the cell answers an admin view after chaos
4	controls: every control journal runs on its booked machines after chaos
4	heal: a control journal keeps a live quorum
4	heal: a journal keeps a live quorum
4	heal: a matchmaker set keeps a live majority
4	leads: a journal keeps a live quorum to take a write after chaos
4	sets: every tenant's set in force is its booked machines after chaos
5	controls: a control journal leaves a wiped machine after chaos
5	heal: a control journal gets every member a live machine can take within the bound
5	heal: a journal gets every member a live machine can take within the bound
5	heal: a matchmaker set gets every member a live machine can take within the bound
5	resolve: every initial member answers after chaos
5	sets: a set with a machine to go to leaves a wiped one after chaos
6	election: the election settles on one renewing leader after chaos
7	chain: cluster converged after chaos
